# dotfiles

Личные dotfiles: zsh, tmux (oh-my-tmux), neovim (AstroNvim), git, ssh,
alacritty, mc, htop. Репозиторий не устанавливает никакие пакеты — он
предполагает, что нужные инструменты в системе уже есть, и занимается ровно
одним: раскладывает конфиги в `$HOME` симлинками через
[GNU Stow](https://www.gnu.org/software/stow/) и помогает держать их
актуальными.

## Структура

```
config/       — сами dotfiles, разложенные как stow-пакеты (git, mc, nvim,
                tmux, zsh, alacritty, ssh, htop) — путь внутри каждого
                пакета зеркалит его цель относительно $HOME, например
                config/git/.config/git/.gitconfig -> ~/.config/git/.gitconfig
deploy.sh     — раскладывает конфиги (deploy) / забирает правки обратно (adopt)
```

## Требования

- bash, git
- [GNU Stow](https://www.gnu.org/software/stow/) — ставится штатным
  пакетным менеджером, сам репозиторий его не устанавливает:
  - macOS: `brew install stow`
  - Debian/Ubuntu: `apt install stow`
  - Fedora: `dnf install stow`
  - Arch: `pacman -S stow`
  - openSUSE: `zypper install stow`
  - Alpine: `apk add stow`

## Быстрый старт

```bash
git clone <repo-url> ~/dotfiles
cd ~/dotfiles
./deploy.sh
```

Раскладывает симлинки из `config/` в `$HOME`. Идемпотентно — можно запускать
повторно. Существующий на месте цели обычный файл (не симлинк) бэкапится с
суффиксом `.bak-<timestamp>`, существующий чужой/старый симлинк — просто
заменяется.

## Использование

### ./deploy.sh

Раскладывает все stow-пакеты из `config/` в `$HOME`.

### ./deploy.sh adopt

Если какое-то приложение переписало путь поверх симлинка обычным файлом
(типичный кейс — GUI-настройки, которые сохраняют файл напрямую), эта
команда через `stow --adopt` затягивает такой файл обратно в `config/`
(заменяя там текущее содержимое) и восстанавливает на его месте симлинк.
Дальше сам смотришь, что реально изменилось, и коммитишь:

```bash
./deploy.sh adopt
git diff
git add -A && git commit -m "..." && git push
```

### Добавить новый конфиг

Просто положи файл по нужному пути внутри `config/<пакет>/<путь-относительно-$HOME>`
(например `config/foo/.config/foo/config.toml` для нового пакета `foo`, или
в уже существующий пакет). Набор пакетов и путей определяется самой
структурой каталогов — правок в `deploy.sh` не нужно, `./deploy.sh`
подхватит новый файл сам.

## Как это устроено

Каждый подкаталог первого уровня в `config/` — отдельный stow-пакет, а путь
внутри него зеркалит цель относительно `$HOME`. `deploy.sh` передаёт все
пакеты в `stow` одним вызовом (а не по одному), чтобы stow не сворачивал
общие каталоги вроде `~/.config` в симлинк на первый попавшийся пакет —
так каждый пакет получает свою часть дерева независимо от остальных.
